# D1, D2 and the confirmation run: design note for their registrations (not registrations)

Written 2026-11-13 so that the designs survive a context change. Nothing computed from a run. Each becomes a draft [REG] with configs as new files, then rule F, owner-proxy, [DECISION] (delegate). All three depend on REG-19's [RESULT] for their seeds, never for their thresholds.

## D1: the burst under a session cap (C2's first loop cut)

- **Runs.** REG-19's burst config with `workload.sessions.cap: <value>` and nothing else changed, on the first three seeds, in REG-19's run order, whose closed burst run is cold and backlogged at the end (`k1.cold_backlogged`) and whose control recovered. The cap's value per seed: `cap.max_sessions_in_service` on that seed's REG-19 control (the owner's rule, decisions.md 2026-11-12 [DECISION], design choices, item 2), computed once after REG-19's [RESULT]; the capped config is written then as a new file (`burst_l1pl350clcap_r2.0_w3000_s<seed>.yaml`).
- **Readout.** K1's readout on the capped run's end window (`k1.cold_backlogged`: reuse, server waiting line, KV), which uses no latency; the wait at the cap is reported apart (`cap.cap_wait`), and the sessions still waiting to start at the end.
- **Labels.** Per seed `cap_recovered`, `cap_cold`, `cap_partial`, `undefined`. Matrix: "loop cut" if at least 2 of 3 are `cap_recovered`; "not cut" if at least 2 of 3 are `cap_cold` (by `docs/claims.md`, stuck runs that stay stuck under the cap refute C2); otherwise "mixed".
- **Prediction (BELIEF).** Cap values 15–20 (the controls on record had 12–14 sessions in service on average before the burst; their maxima are not computed). Each capped run `cap_recovered` ≈ 0.8: with at most that many sessions in service their latest contexts are at most about 20 × 3072 = 61k tokens of a 96,656-token pool, so once the burst's requests have left the prefixes survive. Prior results in the same direction: Huang and Liu 0 of 10 collapsed under a session cap (§3); Valse and Jannesari 30 of 30 capped runs prevented (§1).
- **Does not need `supports`.** The control is meaningful whenever the uncapped run ends cold and backlogged, whatever REG-19's matrix label; fix `agent/DECISION_TREE.md` accordingly when this is registered.
- **Cost.** 3 × ≈ 1.15 h ≈ 3.5 GPU h.

## D2: the same burst with caching off (C2's second loop cut)

- **Which capacity (the registration must fix it; fixed here):** the keep-up capacity with caching off, μ_off = 1.0 req/s by the configs' rule on REG-8's grid (RUN(the 13 REG-8 runs, gate.reg8_zone)), not the saturation floor 1.681. The test load is 2.0 / 2.4 = 0.83 of the closed-loop warm keep-up value, so the control runs at 0.83 req/s (the plan's rule, decisions.md 2026-11-12 [CORR], audit item 1). Known weakness, to state: the grid's next rate, 1.5, failed keep-up, so the true keep-up capacity lies between 1.0 and 1.5 and 0.83 may be as little as 0.55 of it; a second arm at 0.80 × 1.681 = 1.34 req/s (Huang and Liu's choice: "about 80% of the no-cache engine's capacity") is the stricter control and is run if hours allow.
- **Runs.** Closed-loop turns, `--no-enable-prefix-caching`, the same absolute burst (2.4 req/s of 2944-token prompts for 180 s from 900 s), seeds 15, 16, 17, a 1500 s watch (2580 s runs). Burst run only; it is judged against its own baseline.
- **Readout.** No verdict by percent fast: with caching off every turn prefills 2176 to 3968 tokens, so TTFT is near or above 1.0 s even unloaded and the baseline would be `bad_baseline`. Judged on the server's waiting line and the owed backlog: `drained` if the end window's mean waiting is at most baseline + 1.0 (the verdict's `recovered_q_excess`) and the owed backlog at the end is at most its value at the trigger plus one end window's noise (to be fixed in the [REG]); else `backlogged`.
- **Prediction (DERIVED, BELIEF as a forecast).** The burst is 432 requests of 2944 tokens, about 246 s of work at the cache-off token rate (1.681 × 3072 tokens/s). At 0.83 req/s the spare capacity is 0.85 req/s, so the backlog clears within about 10 minutes of the burst's end; at 1.34 req/s within about 25. `drained` in 3 of 3.
- **Also reported.** The uncached-token work rate while the line is non-empty (REG-21's statistic) in a run with dev mode on and caching off, which separates dev mode from the cold state in REG-21's first alternative.
- **Cost.** 3 × ≈ 0.75 h ≈ 2.3 GPU h (4.5 h with the second arm).

## The confirmation run (conditions 5 and 6 at λ = 2.0), only after `supports` or `supports_edge`

- **Design.** REG-15's, at λ = 2.0: baseline 600 s, burst 900–1080 s, a 4500 s watch, then λ = 1 for a drop sized beforehand, then λ = 2.0 for 1500 s. Its control on the same schedule runs second, and only if the burst run is `stuck` at the watch's end (otherwise condition 5 has failed and the control decides nothing).
- **Drop length (the plan's rule: expected backlog and the cold floor, with a factor of two; `gate.reg16_seed_rule`'s form).** From REG-15's calibration on record (decisions.md 2026-11-10 [REG] REG-16: owed 28 at the trigger; c_watch 1.758, c_drop 1.672; lowest 600 s rates 1.728 and 1.637): expected owed backlog at the watch's end ≈ 28 + (2.0 + 432 / 4680 − 1.758) × 4680 ≈ 1560 requests; it drains at about 1.672 − 1.02 = 0.65 req/s, so in about 2400 s; pessimistic (rates lowered by 0.05 from the lowest): ≈ 1940 requests at 0.57 req/s, 3400 s; plus 1200 s to watch the cache warm. The shortest of 3600, 5400, 7200, 9000 s that fits is **5400 s** (DERIVED; to be recomputed by the committed rule on the chosen seed's schedule). Run length 1080 + 4500 + 5400 + 1500 = 12,480 s ≈ 3.5 h.
- **Seed rule (fixed before any schedule is read).** The lowest unused seed from 20 up whose four judged windows plan within 5 % of 2.0 (`gate.reg16_judged_windows`), whose control schedule has no 120 s planned-rate peak of 3.2 or more before the drop (REG-18's exposure rule), and whose pessimistic empty time leaves 1200 s of the drop.
- **Outcome.** `gate.reg15_outcome` (`confirms`, `no_return`, `drop_inconclusive`, `reformed`, `not_persistent`, `bad_baseline`, `inconclusive`), with the phases read from the config (a new function: `reg15_phases` is fixed to REG-15's 1800 s drop).
- **A blind K3 prediction registered with it.** The time from the drop's start until the owed backlog is empty, from Valse and Jannesari's Corollary 3 (busy period = pending work / (1 − λ′/λ_miss)) with REG-21's work rate, against the measured emptying time, within a tolerance fixed there.
- **Cost.** ≈ 3.5 GPU h, ≈ 7 h with the control.
