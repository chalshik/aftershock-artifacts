### Statistic (`analysis/k3w.py`)
- **U** (`work_rate`, FILE(analysis/k3w.py:104)): uncached prompt tokens per second, Σ (prompt_tokens − cached_tokens) over ok requests, session and burst, whose first token falls in the window (the first token ends a request's prefill). It raises if an ok request has no first-token time or no prompt length. U is a mean over the whole window; its values over consecutive 300 s spans, with the lowest and the highest, are reported beside it (`reported_spans`).
- **U_off** (`reference`, FILE(analysis/k3w.py:131)): the mean of U over REG-8's five saturated cache-off runs, pinned by id (FILE(analysis/k3w.py:74): `sweep_l1pl350_pc_off` at λ = 2, 2.5, 3, 3.5, 4, the runs that give the floor 1.681 req/s, RUN(the 13 REG-8 runs, gate.reg8_zone)), each over its measured window. It raises unless exactly those five are there and valid. All five count, and they are not held to the busy precondition; r against the four runs at λ ≥ 2.5 is reported beside r.
- **r** = U over W ÷ U_off, per run. W = [burst end + 600 s, burst end + watch): [1680, 2580) s; [1680, 5580) s for REG-15; [1680, 4080) s for REG-19's runs (DERIVED from the configs: burst end 1080 s, watch 1500, 4500 and 3000 s).
- **Why r:** it contains no turn mix, no residence, no queue discipline and no think time. On synthetic servers (FILE(tests/test_k3w.py:156) onward; no run read): an all-miss first-come-first-served server reads r = 1.00 ± 0.02 at λ = 2.0 and 2.4; so does a running batch of 16 or of 64 slots and a six-fold think time; a fixed cost per turn moves r by under 0.02; a trap at 1.85 or 1.55 req/s reads 1.10 or 0.92; a work rate that differs by load fails J2.
- **Model F's own number** (`docs/model.md` M5): the trapped server works at the all-miss capacity whatever the load, so r = 1.00 and a spread of 0 between loads; with a fixed cost per turn, within 0.02 of that.
- **What r cannot see:** hits below the precondition (r subtracts cached tokens; the precondition, not J1, answers whether the state is all-miss), and prefill done twice after a preemption (each request's tokens are counted once). A run that redoes prefill is credited with less work than it did.

### Alternatives to state with any result
1. **Prefill done twice.** A preempted request is prefilled again; its tokens are counted once. With caching off nothing of the first prefill can be reused; with caching on the freed blocks stay cached until they are overwritten (open-questions S10), which in a full pool is soon. If the two arms redo different shares, r moves by about that difference with no difference in engine speed (the draft-3 review's own synthetic case: 8 % redone in the reference only reads r = 1.08, FILE(docs/drafts/reviews-2026-11-13/rulef-reg21-v3-2.md), its trace a1). The redo proxy of both arms is the readout.
2. **Load and day coincide in batch 1** (above). The λ = 2.0 group has one run of 2026-11-10 and four of 2026-11-11; their r are listed with dates. The fixed-load contrast is the one reading of the same load on other days.
3. **Dev mode.** The burst runs ran with dev mode, the reference sweeps without (PROTOCOL §4; open-questions A6). E1 (cache off, closed loop, no dev mode) and the caching-off control of step D (dev mode) each give a cache-off U in another condition, reported when they exist.
4. **A different saturated state.** The reference is an open-loop sweep whose line grows without bound; the gauges of both arms are reported.
5. **Window edges.** U by first token and by end time, for both arms.
6. **Two differences cancel.** Dev mode or the day could speed the cold arm while redone prefill slows it, and r would read 1 with neither arm at the other's rate. The pieces are alternatives 1 and 3; nothing here separates a cancellation.
7. **A new connection per request.** Every burst config sets `loadgen_force_close`; the reference sweep does not. It is on the client's side; E1 would show it.
8. **Which runs pass the busy precondition may differ by load,** so a J2 outside can come from the selection.
9. **A bimodal set.** A median can sit between two clusters; min, max and SD per group are reported.
10. **The GPU clock, not the cache state.** The run checks enforce the power limit and fail a run on hardware throttling, but ignore the software power cap (FILE(harness/checks.py:15), FILE(harness/checks.py:16)), so the SM clock can differ with temperature and day inside valid runs. Prefill is compute-bound, so U would move about one-for-one with the SM clock (BELIEF). A clock difference between the reference's day (2026-11-07) and the cold runs' days moves r, and so J1's level, for both batches alike; a clock difference between batch 1's λ = 2.0 days (2026-11-10 and 11) and REG-19's days moves the fixed-load contrast, from which the reference cancels (both medians are over the same U_off). A few percent is the size of either tolerance (BELIEF as to the size). The power limit itself is checked per run (FILE(harness/checks.py:188), through `expected_power_limit_w` in FILE(configs/l1_pl350_base.yaml:7)). **This registration does not separate it.** What would: the means of `sm_clock_mhz`, `temp_c` and `power_w` from each run's `gpu.jsonl` (FILE(harness/recorder.py:66)) over W and over each reference run's measured window; that readout is not computed under REG-21.
11. **Selection on the outcome within one load.** The preconditions keep the runs that stayed cold, backlogged and busy, and a run whose engine ran slower is likelier to stay so; that biases J1's median low by a fraction of the run-to-run SD (BELIEF). The runs left out at each load are listed with their reason and, where it exists, their r.
