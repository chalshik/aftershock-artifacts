- **Batch 2 not computed.** After REG-19's final result, every raise once `reg21_table(2)` has been entered and before the table is printed, wherever it comes from (`batch2_runs` with all it calls, the seal included, `reference`, `select`, `row`, `judge`, or batch 1's recomputation for the contrast), gives "batch 2: not computed", with the reason: for example a gap in the seeds, two valid runs of a seed, fewer than three seeds, a folder matching either pattern that cannot be loaded (`find_runs` loads every matching folder before it looks at validity, so a lost run's cut file or missing `env.json` stops it), an ok request without a first-token time, a sixth valid reference run at a rate of 2.0 or more, or a result heading the seal does not accept. If the heading of REG-19's final [RESULT] is one that `withheld.lifted('[RESULT] REG-19')` does not accept, batch 2 is not computed whether or not the command was run; no heading is added to make the seal lift. Batch 2 is also not computed, with the reason, if REG-19 ends without the table that `analysis.gate reg19` computes (an operational stop, or spent attempts); if, after REG-19's table is first computed or read by anyone (its final [RESULT] at the latest) and before batch 2, an entry changes the seeds that table counts or the validity flag of a run matching the batch-2 pattern (a flag set before that is part of what that table counts and does not end batch 2); or if duty (a) below is breached. **The time of that cut comes from a record made then, not from memory.** Here "REG-19's table" is any output, by any entry point (`python -m analysis.gate reg19`, `python -c`, a REPL, another module), of `reg19_table()` whose `seeds_run` is not empty or of `reg19_pair` for a REG-19 seed, from any checkout and however many of REG-19's seeds it holds: a run made in the middle of the matrix counts, and so do one from the pinned worktree, which has no seal, and one on `main` with `AFTERSHOCK_UNSEAL=REG-19` (FILE(analysis/withheld.py:51)). Only output computed on REG-19's own run folders counts (this repository's `runs/`, the pinned worktree's links to them, or a copy of them); output on synthetic folders (tests, the scripts' sandbox) is not REG-19's table, and the saving duty below does not apply to it. A run that raised printed nothing (`gate`'s `__main__` prints once, at the end, FILE(analysis/gate.py:2107)), and a run whose `seeds_run` is empty (the seal, or no `runs/`) printed nothing of REG-19; neither is REG-19's table, and `reg19_step`'s `done` and `continue` are not either. From this entry on, whoever produces REG-19's table saves its stdout verbatim to a file whose name carries a UTC time taken no later than the command's start, and its stderr beside it, both in `docs/probe/20261113_reg19/ops_r3/state/` (REG-19's script already does, with the stamp it takes before its recheck: `reg19_final_<UTC stamp>.txt` and `reg19_final_err_<UTC stamp>.txt`, FILE(docs/probe/20261113_reg19/ops_r3/final.sh:20)); a run by hand takes its stamp with `date -u` in the same command line that runs the table, and the record's commit message quotes that line. The two files are committed at once, alone, on the branch that holds this entry. The files of a run that raised go in with the [OPS] entry that `final.sh` requires before a second try (FILE(docs/probe/20261113_reg19/ops_r3/final.sh:31)); "set aside" there means both files are moved out of `state/`, since `final.sh`'s check matches either (FILE(docs/probe/20261113_reg19/ops_r3/final.sh:18)). **The record** is the saved stdout of the first run that gave REG-19's table; **the record's commit** is the first commit that adds that file to the branch that holds this entry. A record committed late, without its stderr file, or together with other changes is still the record: that is a breach of the duty above, which the batch-2 [RESULT] reports, and every other change in the record's commit counts as after the cut. If the record's stamp is later than its commit's committer time, the breach is reported and batch 2 is labelled retrospective: the cut is never later than the true start, and no other time takes the stamp's place. The record's output lists the seeds run with their runs (`rows[].runs`) and the seeds left out of n (`excluded`); if they are not the seeds REG-19's final [RESULT] counts (a record from the middle of the matrix), duty (b)'s lists differ and batch 2 is not computed. **The cut is the UTC time in the record's file name.** For this bullet, for duty (a), for the stopping rule's bullet "From this entry to batch 2" and for "What was known", a change or an entry counts as made before the cut only if the commit that makes it is a strict ancestor of the record's commit (an ancestor other than the record's commit itself) and its committer time is earlier than the cut, the two compared as instants (the committer time as git's `%ct`, epoch seconds; the stamp read as UTC; this Mac commits at +0600, so local clock readings are never compared); a commit in the same second as the stamp counts as after; anything else counts as after it, a change in the record's own commit included. The stamp and the commit times both come from the Mac's clock (`final.sh` runs there). No commit from this entry to batch 2 is amended or rebased, and no committer date is set by hand. A rewritten commit is judged by its new committer time, like any other, so one rewritten after the stamp counts as after the cut; a commit whose committer date was set by hand counts as after the cut. **If REG-19's table was computed or read and there is no record, batch 2 is not computed, with that reason** (the third list of duty (b) does not exist). There is no record if the first run that gave REG-19's table was not saved under a stamp taken as this bullet requires (no later than the command's start; `final.sh`'s stamp qualifies); a later saved run does not take its place. A saved record that is not yet committed when batch 2 is to be computed or declared not computed is committed first (late: a breach, reported, and still the record). "No record" never follows from leaving a saved file uncommitted, and no saved `reg19_final_*` file is deleted or moved out of the repository, except a failed run's pair as "set aside" says. A saved record lost against that rule is a breach, reported; the cut is then unknown, and batch 2 is not computed, with that reason. The batch-2 [RESULT] cites the record's file name (the cut) and commit hash, the ancestry check (`git merge-base --is-ancestor`) of every commit this bullet relies on and their committer times (`%ct`) beside the cut, lists every `reg19_final_*` file git has held, with its stamp and commit (`git log --all --name-status -- 'docs/probe/20261113_reg19/ops_r3/state/reg19_final_*'`; those set aside included), and states that no run that gave REG-19's table is known to have started before the record's stamp (a pair set aside and never committed, against the rule above, cannot be detected: a limit). These are facts in git that anyone can check: if the [RESULT] leaves one out or quotes one wrongly, a [CORR] adds or corrects it, and the omission never changes a label. The label follows from the facts alone: with no record, batch 2 is not computed (above); a commit this bullet relies on that is not before the cut has the consequence its own rule gives ("What was known", duty (a), the stopping rule's bullet "From this entry to batch 2"). These compute nothing and are not covered by this bullet: the clean-tree refusal (`_dirty`), a batch argument other than 2, a failure before `reg21_table` is entered (`uv`, the environment, an import), and an interruption from outside the code (a signal, a killed process, a machine that stops; a `MemoryError` and a `KeyboardInterrupt` count as interruptions too); they follow the fix clause above, with no change to the judged path or to `analysis/k3w.py`, and the command is run again. The fix clause does not apply to any of the cases that give "not computed": no change of `batch2_runs`, of `find_runs` or the loader, of the pattern, of a heading or of a run's validity flag follows one, no folder is added, moved or changed to make the selection pass, and there is no rerun. (Before REG-19's final result the seal's raise means only that the command was run too early; nothing is computed and nothing is spent.)
