| # | Question | Answer (source only) | Evidence |
|---|---|---|---|
| S8 | What unit do `vllm:prefix_cache_queries` and `vllm:prefix_cache_hits` count, and which requests do they include? | **Tokens.** Queries add `request.num_tokens` (the prompt, for a new request); hits add the locally cached tokens found at admission. **A previously preempted request is left out:** when it is admitted again, its numbers go to separate `preempted_*` fields, which these two counters do not export. So h is token-weighted, and the re-prefill after a `preempt` wipe does not show in h. Counted once per admission, not per scheduling step | `v1/metrics/stats.py:120-155` (`PrefixCacheStats.record`, "`queries`: Refers to the number of tokens that were queried"); `v1/core/kv_cache_manager.py:253-262` (`record_prefix_cache_stats`, `preempted=request.num_preemptions > 0`); `v1/core/sched/scheduler.py:1314-1318` ("Record at admission"); `v1/metrics/loggers.py:661-679`, `:1167-1172` (only `.queries` and `.hits` exported, documented "in terms of number of queried tokens" / "cached tokens") |
| S9 | In what order are cached blocks evicted? | **Approximately LRU by release time, tail blocks first.** Free blocks sit in one queue; new blocks are taken from its front (`popleft_n`), and taking a block that still has a hash evicts it from the cache. When a request frees its blocks, they are passed in reverse order (its tail first); blocks with a hash are appended to the back ("FIFO reuse of cached blocks for LRU eviction behavior"), blocks without one are put at the front, to be reused first. A cache hit on a free block removes it from the queue (`touch`); it rejoins the back when freed again. So the oldest-released prefix is evicted first, and within one request the last blocks go before the first ones (the shared start of a session survives longest) | `v1/core/block_pool.py:666-689` (`get_new_blocks`, `_maybe_evict_cached_block`), `:752-768` (`touch`), `:774-803` (`free_blocks`); `v1/core/single_type_kv_cache_manager.py:588-589`; `v1/core/kv_cache_manager.py:620-629` |
| S10 | Do a preempted request's blocks stay cached? | **Yes, until they are reused.** `_preempt_request` frees the request's blocks through the normal free path and sets `num_computed_tokens = 0`. Full blocks keep their hash, so they go to the back of the free queue as cached eviction candidates, and the request can hit them on readmission (counted under `preempted_*`, S8). **Exception: the `preempt` wipe.** `reset_prefix_cache(reset_running_requests=True)` first preempts every running request, then resets the pool's cache, so nothing it held stays cached | `v1/core/sched/scheduler.py:1571-1593` (`_preempt_request`), `:2766-2775` (`_free_request_blocks`), `:2840-2868` (`reset_prefix_cache`); `v1/core/block_pool.py:774-803`, `:827-866` (`BlockPool.reset_prefix_cache`: removes every hash, succeeds only when no block is held) |
| S11 | Does a miss refill the cache by itself? | **Yes.** When blocks are allocated for a scheduled step, the blocks covering the computed tokens, up to `request.num_tokens`, are committed to the cache right away (`cache_blocks`), not when the request finishes. So a turn that misses caches its own prompt as it is prefilled, and the session's next turn can hit it if those blocks are not evicted in between. `request.num_tokens` also covers generated tokens, so the output's full blocks are cached too; with recorded replies they never match a later turn | `v1/core/kv_cache_manager.py:607-616` (`num_tokens_to_cache = min(total_computed_tokens + num_new_tokens, request.num_tokens)`); `v1/request.py:295-296` (`num_tokens` = all token ids) |
