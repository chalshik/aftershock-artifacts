1. **Seed 18's control is rerun unchanged, as attempt 2; and the attempt rule is completed now (F6, P6).** REG-19's stopping rule: "Each run once; an invalid run (other than `burst_min_kv_max`) is rerun unchanged, at most twice; no rerun on any verdict or label … A rerun decision reads only `checks.json`." The registration does not say how a run counts that left no `checks.json`. Fixed here, before any such case recurs: **every launch of a config counts as one attempt of it, whether it ends valid, invalid or without a `checks.json` (the VM going off, the server not starting); a config has at most three attempts; a folder without `checks.json` is kept and not opened; when a config's attempts run out the queue stops** ("a seed with no valid pair after its reruns stops the queue"). This is the stricter reading: the lost run spends one of seed 18's control's three attempts. Nothing is read from the lost run. Worst case if every remaining run needed all its attempts: 11 runs × 4188 s ≈ 12.8 GPU h plus cooling, against 4.7–4.9 h expected.

3. **Power limit: the launch no longer sets it (F4).** REG-19's stopping rule stops the queue on "a limit other than 350 W". Draft 1's launch script set 350 W before every run, which would have hidden a reboot between runs. Now: `session_probe.sh` runs once before the queue and records the VM's boot id, uptime, kernel, driver, CPU governor, the limit, the tree and free disk; it stops unless the limit reads 350.00 W. `launch8.sh` only reads: a limit other than 350.00 W, or a boot id other than the session probe's, stops the queue. The one allowed root command (`sudo -n nvidia-smi -pl 350`) is in `session_probe.sh` behind `SET=1`, runs only with no compute process on the GPU, and records the limit before and after. **On 2026-11-12 19:53 UTC that command failed on the VM ("a password is required"; `/etc/sudoers.d/` holds only its README), so today the owner must set 350 W;** the agent starts no run at another limit.
