- **Question:** at λ = 2.0 (setup L1, 350 W, closed-loop turns), on the five seeds whose burst runs all ended `stuck` under REG-19 (FILE(docs/decisions.md:16533-16537)), does the same burst leave the server cold at the end of the 3000 s watch when the sessions in service are capped at the highest number the same seed's no-burst control had in service at once?

### What D1 can and cannot do (rule A1), said first
- **What it can decide.** Whether REG-19's stuck state survives when the population in service is held at the healthy peak (prevention: the cap is on from t = 0). The prior work on record tests rescue, with the cap applied after the collapse: Huang and Liu's session cap 0 of 10 and an admission-only cap 2 of 8 (FILE(docs/decisions.md:3980), FILE(docs/decisions.md:4224)); Valse and Jannesari's arrival stop against the in-trap cap 9 of 9 (FILE(docs/decisions.md:4227)); all BELIEF as to the papers (open question A16). D1 says nothing about rescue.
- **What it cannot decide: the cap does not cut one link.** Under closed-loop turns the server is offered what its sessions release, in both arms: REG-19's clients released 1.643–1.887 req/s while the server completed 1.703–1.777 (FILE(docs/decisions.md:16540), FILE(docs/decisions.md:16558)). The cap changes how many sessions are in service, and so the running batch (N), the pool (KV) and the time a prefix sits idle between turns, all at once; it does not change the long-run session arrival rate (0.25 sessions/s, DERIVED: λ 2.0 ÷ 8 turns). So D1 cannot separate "the cap cut the loop at the KV link" from "the cap cut it at the batch link", and it cannot separate either from "admission control helps any bistable server whose fast state is above the load and whose slow state is below it". It can separate two things (next bullet). The caching-off control (D2) is the other half of C2's test; D1 alone does not make C2 "supported".
- **The admission confound, stated plainly.** A cap moves waiting from the server to the client. That is what a cap is, so D1 does not try to rule it out; it asks whether the waiting it moves ever clears. Two readouts separate the cases D1 can separate:
  1. *Moved and still stuck* against *moved and cleared*: the cap's own queue (`d1.cap_queue`, sessions with `t_arrived` ≤ t < `t_admitted`) in the end window against its baseline. A server that stays cold completes about 1.75 req/s (REG-19's c over W, 1.740–1.758, FILE(docs/decisions.md:16533-16537)), below the load of 2.0, so it cannot drain the cap's queue; a queue back at its baseline means the server left the cold state (DERIVED; BELIEF that the cold completion rate does not rise under a cap, which `spans`' `completion_rate` reports).
  2. *Never cold* against *cold, then warm*: `d1.load_reading` (reported) finds the first 300 s span after the burst's end whose prefix reuse is back within 0.06 of the baseline, and reports the cold spans before it with the server-side arrival rate against the open-loop floor 1.681 req/s (FILE(analysis/k2.py:24)) and against the same span of the same seed's uncapped REG-19 run.
  What D1 cannot separate, and will say in its [RESULT]: a cap that prevents the cold state from forming (a smaller effective shock, since the cap holds back session turns during the burst) from a cap that lets it form and then breaks it. Both are prevention; `load_reading`'s `never_cold` and `in_window` name which one each seed showed, and `gate.shock_size` is reported for both arms.
- **The server's waiting line cannot fail under the cap, and the pool probably cannot fill.** With the cap at about 23–31 sessions (BELIEF, "Prediction"), a cold server saturated at x ≈ 1.75 req/s holds about x × 5 s = 8.75 sessions in think time (Little's law on that stage; mean gap 5 s, `configs/gap5_base.yaml`), so at most cap − 8.75 requests are in flight, far below `--max-num-seqs` 256 (FILE(configs/stage2_cap_base.yaml:6)): the server's waiting line stays near 0 in every state while the pool is not full, so its clause in the label is met by construction (DERIVED from that bound; BELIEF as a model). At the cold state's KV per running request (0.951 ÷ 30: REG-22 batch 2's end windows, KV 0.950–0.952 at N 29.80–30.29, FILE(docs/decisions.md:16752-16756)) the pool stays below condition 4's 0.80 for any cap below 33.99 and below 0.95 for any cap below 38.72 (DERIVED: `d1.first_order`, 8.75 + 0.80 × 30 ÷ 0.951 and 8.75 + 0.95 × 30 ÷ 0.951; PROBE(docs/drafts/d1_r1/inputs_20261114.txt) is the table, model BELIEF). So under the expected caps **the KV link is cut by construction, and D1 tests whether the cache comes back once the pool is not full.** That can still fail: a seed that stays cold with the pool below 0.80 is `stuck_kv_free`, which refutes the KV link as what sustains the stuck state. A cap above about 34 (if a control's peak is that high) could let the pool fill; a seed that stays cold with a full pool is `stuck_kv_full`, which says the cap did not cut the KV link. The cap values are known before any capped run (the registered computation, below), so the [RESULT] states which regime each seed was in before its label is read.
- **Prediction, decisions and cost** (A1; full text below): per valid seed P(cut) ≈ 0.78 and P(stuck under the cap) ≈ 0.05 (BELIEF); E[k_cut] ≈ 3.9 of 5; P(`supports`) ≈ 0.74, P(`mixed`) ≈ 0.26, P(`refutes`) ≈ 0.001 (DERIVED by enumeration from those beliefs). `supports` lets C2's status say that the cap prevented the stuck state (with the confound above in the same sentence); `refutes` or `cap_did_not_cut` changes C2's status the other way; `mixed` changes nothing and goes to the owner. ≈ 6.2 GPU h, ≈ 7.7 h expected with reruns.

### The cap's value (registered computation, once, before any capped run)
- **Rule (the owner's, FILE(docs/decisions.md:3949)):** per seed, the highest number of sessions in service at once in the same seed's no-trigger control, a session being in service from its first turn sent to its last reply. Code: `analysis/cap.py`'s `max_sessions_in_service` (an exact event sweep, ends before starts at equal times, burst rows excluded; FILE(tests/test_session_cap.py:191)), wrapped by `d1.cap_value` (raises below 1).
- **Inputs, pinned:** REG-19's counted controls, one per seed (FILE(docs/decisions.md:16533-16537)): 15 `20261112-050920_stage2_control_l1pl350cl_r2.0_w3000_s15`, 16 `20261112-073516_…_s16`, 17 `20261112-103423_…_s17`, 18 `20261113-165516_…_s18` (attempt 3; the lost attempt 2, `20261113-033842_…_s18`, is outside every count, FILE(docs/decisions.md:16567), and never read), 19 `20261113-192110_…_s19`. `d1.control_run` refuses a run that is not valid or whose config is not REG-19's seed control (seed, name, no trigger, closed loop, no cap, rate 2.0, duration 4080). FILE(tests/test_d1.py), `test_pinned_runs_are_reg19s_counted_ten`.
- **This is new analysis of existing runs, so it is registered here and computed after this entry is approved** (rule A5, rule C): `uv run python -m analysis.d1 caps`, once, from committed code, its output saved under `docs/probe/d1/` and committed alone with an [OPS] entry quoting it. It prints per seed the cap, the time the control first reached it, its peak before the burst's start (900 s), its mean sessions in service over [300, 900) s and the first-order KV bound at that cap (`d1.cap_values`), then a `caps` line. `python -m analysis.d1 configs <that file>` then writes the five configs, committed with an [OPS] entry. No rule, label or threshold of D1 may change after the caps are seen; a change is a [CORR] and goes back to rule F.
- **Does the cap bind in the capped run before the burst?** (point 3 of the brief) Before 900 s the capped run's schedule is the control's (above), and the server is the same, so the in-service count before 900 s differs from the control's only by latency jitter in the closed loop (turn k is released at the end of turn k − 1 plus its planned gap, FILE(harness/loadgen.py:139-140,158-160)). The cap is the control's whole-run peak, at least its pre-burst peak, so the cap binds before the burst only if jitter lifts the count above the control's whole-run peak; that needs the control's peak to lie before 900 s or within jitter of it. The caps computation prints `t_peak` and `peak_before_burst` for each seed, so the margin is on record before any capped run. In the run it is reported, never judged: `d1.waits(run)["before_burst"]` (`cap.cap_wait` over the sessions that reached the cap before 900 s) and the cap queue's baseline mean in the label's values. The guards that apply: the baseline pf check (`bad_baseline` below 0.98) and `gate.reg19_baseline_pair` against the control. Prediction (BELIEF): P(any wait before 900 s) ≈ 0.15 per seed, and when there is one, under 2 s of waiting in total.

### What is measured: one label per capped run (`d1.label`), then the matrix (`d1.outcome`)
- **Windows** (`k1.windows`, REG-19's): baseline [300, 900) s, end window [3480, 4080) s, the window before it [2880, 3480) s; thresholds are the verdict's registered ones (FILE(configs/stage2_base.yaml:15-20), FILE(configs/stage2_cap_base.yaml:8-11)): `min_baseline_pf` 0.98, `recovered_hit_drop` 0.06, `recovered_q_excess` 1.0, `stuck_hit_drop` 0.06, `hit_climb` 0.06, `drain_horizon_s` 3600. Condition 4's `min_kv` 0.80 (FILE(analysis/c2.py:30)). No threshold is new.
- **Inputs:** the prefix reuse of later turns (`c2.reuse_in`, at least 20 turns, FILE(analysis/c2.py:34,62-65)) in place of the hit counter, whose served mix includes first turns and burst requests (decisions.md 2026-11-05 [CORR]; REG-20's readout); the server's mean waiting line and pf (`load._level`); the cap's queue (`d1.cap_queue_level`, mean and slope on a 1 s grid); mean KV in the end window (`c2.gauge`).
- **Labels, in this order:** `unclear` (baseline pf missing) → `bad_baseline` (baseline pf < 0.98) → `unclear` (any input missing) → if the server is warm (end reuse ≥ baseline reuse − 0.06 and end waiting ≤ baseline + 1.0): `recovered` (cap queue's end mean ≤ its baseline mean + 1.0), else `unclear` (no slope), else `recovered_cap_draining` (slope < 0 and the queue would empty within 3600 s), else `server_only` → `unclear` (reuse of the window before missing, so a climb cannot be ruled out) → `rewarming` (end reuse − previous reuse ≥ 0.06) → if end reuse ≤ baseline − 0.06: `stuck_kv_full` (end KV ≥ 0.80) or `stuck_kv_free` (end KV < 0.80; `unclear` if KV is missing) → `unclear`. Tested class by class (FILE(tests/test_d1.py), `test_warm_server_and_empty_cap_queue_is_recovered` to `test_bad_baseline_and_missing_values`), including that an empty server line alone never makes a recovery (`test_cold_reuse_with_an_empty_server_line_is_stuck_not_recovered`) and that the label reads reuse, not the hit counter (`test_the_label_reads_reuse_not_the_hit_counter`).
- **Cut** = `recovered` or `recovered_cap_draining`. **Stuck under the cap** = `stuck_kv_free` or `stuck_kv_full`.
- **`harness_fault`** (needs the owner's approval: it removes a run from n beyond the automatic checks, CLAUDE.md rule C): the records show more sessions holding a slot than the cap (`d1.slots`, `max_held`, from admission to last reply), or sessions waiting at the cap while a slot stood free in more than 5 % of the waiting grid seconds (`idle_share`; a hand-over takes milliseconds, a leaked slot stays free) (`d1.harness_fault`). Such a run is listed and leaves n; it is not rerun under this entry (its cause needs an [OPS] or [CORR] first). If this label is not approved, the same run counts in n as `unclear`.
- **Why not REG-19's whole-window test** (`gate.reg19_seed_outcome`)? Its first clause labels a seed whose server line emptied for 30 s as not stuck through the watch (`emptied_*`), and its cold side compares the completion rate over W with the load (FILE(docs/decisions.md:3790,3792)). Under the cap the server's line is held near 0 and its completions are throttled by construction (above), so every capped seed would "empty" and its cold side would be read for the cap's reason, not the server's. D1 keeps REG-19's windows, thresholds and seeds, and reads the server on reuse and the client side on the cap's queue. REG-19's verdict (`load.verdict`) is reported for both arms, never judged ("Reported, never judged").
- **The matrix** (`d1.outcome`; `harness_fault` leaves n), rules in this order, with most = 3 (REG-18's and REG-19's "most seeds"):
  1. `too_few`: n < 3 valid labelled runs.
  2. `refutes`: `stuck_kv_free` ≥ 3.
  3. `cap_did_not_cut`: `stuck_kv_full` ≥ 3.
  4. `supports`: no seed stuck under the cap and cut ≥ 3.
  5. `admission_only`: `server_only` ≥ 3.
  6. `mixed`: anything else.
  `bad_baseline`, `unclear` and `rewarming` count in n, neither cut nor stuck. One stuck seed blocks `supports` because claims.md counts any stuck run under the cap against C2 (FILE(docs/claims.md:27)). FILE(tests/test_d1.py), `test_outcome_rules` (10 cases).
- **Rule H:** k of n per class with the one-sided 95 % Clopper–Pearson upper bound from `analysis/stats.py` (`cp_upper`), on the share stuck and on the share cut, and the lower bound on the share cut (1 − upper(n − k, n)). ### Decision under each outcome (rule A1; C2's status line and the paper each need their own reviewed decision, `agent/FOR_AUTHOR.md`)
- **`supports`:** the agent drafts C2's status line: "At λ = 2.0 (L1, 350 W, closed-loop turns), the session cap at each seed's healthy peak prevented the stuck state in k of n seeds (bounds), where the same burst without the cap left all five stuck (REG-19). The cap holds the whole population in service, so it cuts the running batch and the pool together, and it moves waiting to the client; D1 does not say which link mattered. The caching-off control is not run." D2's registration becomes the next C2 step. The paper may say the stuck state "needs a population above the healthy peak", not that the KV link is shown to be the cause. Alternatives to state with it (rule A2): (a) the loop was cut (C2), separated from (b) a smaller effective shock (the cap held back session turns during the burst) by `load_reading` (`never_cold` against `in_window`) and `gate.shock_size` in both arms; (c) day or drift (the capped runs run days after REG-19's), separated only partly by `gate.reg19_baseline_pair` against the control and the baseline completion rate; an uncapped rerun would separate it and is not in D1 (an open point for the owner).
- **`refutes`:** C2's status line drafts "stuck under the session cap with the pool below 0.80 in k of n seeds: the stuck state does not need a full pool, so the KV link of C2's loop is not what sustains it at this cell." Alternatives (rule A2): (a) as stated; (b) the KV gauge counts only blocks of running requests, so prefixes can be evicted by churn in a pool that reads below 0.80; separated by `c2.eviction_readout`'s residency histograms and turn spacing, reported for each seed; (c) the cap path itself slows sessions (a harness fault not caught by `harness_fault`), separated by `idle_share` and `waits`. No further loop-cut run until the owner decides.
- **`cap_did_not_cut`:** the pool filled under the cap, so the first-order bound was wrong (KV per running request higher in a capped cold state, or caps above 34). By claims.md's wording ("stuck runs that stay stuck under the session cap", FILE(docs/claims.md:27)) this refutes C2; by D1's design the cap did not cut the KV link, so it is not the test intended. The [RESULT] gives both readings with the end-window KV and N per seed, and the owner decides C2's status. The caps were on record before the runs, so a cap ≥ 34 is not a reading made after the data.
- **`admission_only`:** the server's reuse came back but the cap's queue kept growing in ≥ 3 seeds. With a warm server the cap is not the bottleneck (DERIVED: cap 26 ÷ ≈ 55 s per healthy session ≈ 0.47 sessions/s against 0.25 arriving; the session length from "Prediction"), so this points first to the cap path (a leaked slot) or a cap far below the prediction. No C2 status change; an [OPS] or [CORR] entry finds the cause before anything else is drafted. Under the owner's rule read on the server side alone ("judged on the server's hit rate and waiting line", FILE(docs/decisions.md:3949)) these seeds would count as cut; `k_cut_server_side` reports that count (readout).
- **`mixed`:** no C2 status change. The [RESULT] reports every class with its bound; the owner chooses between more seeds (a new registration) and reporting D1 as inconclusive.
- **`too_few`:** no judgment; runs reported from `checks.json` only; the owner decides.
- **In no case** does D1 change REG-19's result, REG-22's tables or C1's status.

### Stopping rule (REG-19's and E1's)
- **Order:** seeds 15, 16, 17, 18, 19, one capped run each, fixed before any cap is computed. No interim look at any run's records, verdict or label before the result; no futility stop (none of the outcomes needs one, and an interim look would need its own one-bit rule).
- **Reruns:** an invalid run is rerun unchanged at most twice (three attempts per seed). A `gpu_steady` failure is rerun once after cooling to ≤ 45 °C, and a second `gpu_steady` failure over all D1 runs stops D1. `no_errors`, `power_limit` (a limit other than 350 W) or `manipulation` (the burst did not fill the pool) in a run's `failed` stops D1. Any other check in `failed` of two D1 runs, at any seeds, stops D1 (on the first GPU runs of the cap path a check that fails twice is a question about the harness). A launch that leaves no `checks.json` (a lost run) counts as an attempt and stops D1 until an [OPS] entry records its cause; a lost run is never opened. A pre-launch check that fails spends no attempt.
- **After any invalid run the queue pauses** for a person to read only `valid` and `failed` and restart it.
- **A rerun decision reads only `valid` and `failed`** of `checks.json`; no rerun on any verdict, label or readout.
- **Fewer than 3 valid runs** gives `too_few`; a seed whose attempts are spent is listed in `not_run`.
- **The owner halts D1** by an entry headed `## <date> · [DECISION] (owner) D1 halted`.
- **D1 holds the VM** from its first launch to its end entry (`## <date> · [OPS] D1: the queue ended …` or `… ended by a stop: …`); its place relative to E1, REG-20 arm A and REG-24 is set by RUNBOOK §5 at approval (open point). The launch scripts are a separate ops draft, modelled on E1's (`docs/probe/20261113_e1/ops/`), not part of this draft.
