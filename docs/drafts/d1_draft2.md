### What D1 can and cannot do (rule A1), said first
- **What it can decide.** Whether REG-19's stuck state survives when the population in service is held at the healthy peak (prevention: the cap is on from t = 0). The prior work on record tests rescue, with the cap applied after the collapse: Huang and Liu's session cap 0 of 10 and an admission-only cap 2 of 8 (FILE(docs/decisions.md:3980), FILE(docs/decisions.md:4224)); Valse and Jannesari's arrival stop against the in-trap cap 9 of 9 (FILE(docs/decisions.md:4227)); all BELIEF as to the papers (open question A16). D1 says nothing about rescue.
- **What it cannot decide: the cap does not cut one link.** Under closed-loop turns the server is offered what its sessions release, in both arms: REG-19's clients released 1.643–1.887 req/s while the server completed 1.703–1.777 (FILE(docs/decisions.md:16540), FILE(docs/decisions.md:16558)). The cap changes how many sessions are in service, and so the running batch (N), the pool gauge (KV) and the time a prefix sits idle between turns, all at once; it does not change the long-run session arrival rate (0.25 sessions/s, DERIVED: λ 2.0 ÷ 8 turns). So D1 cannot separate "the cap cut the loop at the KV link" from "the cap cut it at the batch link", and it cannot separate either from "admission control helps any bistable server whose fast state is above the load and whose slow state is below it". Nor can it separate C2's loop from **a failure driven by the population through pool pressure, with or without the prefix cache**: the uncapped stuck runs held ≈ 30 running requests at KV 0.95 with 11–21 preemptions per span (FILE(docs/decisions.md:16540)); preemption and recompute under a full pool would vanish under the cap as well, and only the caching-off control (D2) separates that from C2. D1 alone does not make C2 "supported".
- **The admission confound, stated plainly.** A cap moves waiting from the server to the client. That is what a cap is, so D1 does not try to rule it out; it asks whether the waiting it moves ever clears. Two readouts separate the cases D1 can separate:
  1. *Moved and still stuck* against *moved and cleared*: the cap's own queue (`d1.cap_queue`, sessions with `t_arrived` ≤ t < `t_admitted`) in the end window against its baseline. `recovered` needs that queue back to its baseline + 1, which needs sessions to finish at ≥ 0.25/s, about 2.0 req/s, above every cold rate on record, 1.703–1.800 per span (FILE(docs/decisions.md:16539)); a cold server instead grows the queue by ≈ 0.031 sessions/s, ≈ 19 per 600 s (DERIVED: 0.25 − 1.75 ÷ 8; 0.03125 × 600). So a queue back at its baseline means the server left the cold state (DERIVED; BELIEF that the cold completion rate does not rise under a cap, which `spans`' `completion_rate` reports). The same queue is what makes a cold seed `stuck` (DG1, "Labels").
  2. *Never cold*, *cold only while the burst's own requests were in the system*, and *cold, then warm*: `d1.load_reading` finds the first 300 s span after the burst's end whose reuse is back within 0.06 of the baseline and lists the cold spans before it; `d1.onset_class` names each seed `never_cold`, `burst_only` (cold only in spans that start before the last burst request ended, `c2.last_burst_end`; REG-22 judges no such span, FILE(analysis/c2.py:11-15)), `formed_then_cleared` (a cold span that starts after that exit, then the re-warm) or `undefined`. **Only `formed_then_cleared` bears on whether the cap breaks a sustaining loop** (C2's claim, FILE(docs/claims.md:23)); `never_cold` and `burst_only` show only that the cap prevented the onset, for which a smaller effective shock (the cap held back session turns during the burst) is an equal explanation. `load_reading`'s comparison with the open-loop floor 1.681 req/s separates nothing: with a binding cap and closed-loop turns the server is sent what it completes, so a cold span's server-side rate is its cold completion rate, 1.703–1.800 on record (FILE(docs/decisions.md:16539)), above 1.681, and `in_window` is expected whenever a cold span exists (DERIVED). It is reported, never judged, and is no evidence against admission relief.
- **Departures from the cap rule of record, for the approver.** (1) Item 2 says "The capped arm is judged on the server's hit rate and waiting line; waiting at the cap is reported apart" (FILE(docs/decisions.md:3949)), and the plan expects "`recovered`, with the waiting moved to the load generator" (FILE(docs/experiment-plan.md:423)). D1 makes the cap's queue part of the label: a warm server whose cap queue does not clear is `server_only`, not cut, and a cold reuse without a cap backlog is `partial`, not stuck. Reason: under the cap the server's line is empty by construction, so it cannot tell a cleared state from a moved one. The owner's reading is kept as `k_cut_server_side` (readout). (2) "Hit rate" is read as the prefix reuse of later turns (REG-20's readout, FILE(analysis/k1.py:8)), with the hit counter's thresholds. The approving entry accepts both departures, or restores item 2's reading, before the caps are computed.
- **The server's waiting line cannot fail under the cap, and the gauge probably cannot reach 0.80.** With the cap at about 23–31 sessions (BELIEF, "Prediction"), a cold server saturated at x ≈ 1.75 req/s holds about x × 5 s = 8.75 sessions in think time (Little's law on that stage; mean gap 5 s, `configs/gap5_base.yaml`), so at most cap − 8.75 requests are in flight, far below `--max-num-seqs` 256 (FILE(configs/stage2_cap_base.yaml:6)): the server's waiting line stays near 0 in every state while the pool is not full (DERIVED from that bound; BELIEF as a model). At the cold state's KV per running request (0.951 ÷ 30: REG-22 batch 2's end windows, KV 0.950–0.952 at N 29.80–30.29, FILE(docs/decisions.md:16752-16756)) the gauge stays below condition 4's 0.80 for any cap below 33.99 and below 0.95 for any cap below 38.72 (DERIVED: `d1.first_order`, 8.75 + 0.80 × 30 ÷ 0.951 and 8.75 + 0.95 × 30 ÷ 0.951; PROBE(docs/drafts/d1_r1/inputs_20261114.txt) is the table, model BELIEF). So under the expected caps **the running batch is held near the healthy level and the pool gauge below condition 4's 0.80 by construction; eviction is not cut by construction.** The gauge counts only blocks held by running requests, and cached free blocks stay in the free queue and are evicted about least recently used first (open questions S7 and S9: FILE(docs/open-questions.md:25), FILE(docs/open-questions.md:34); SOURCE(vLLM 0.32.0 v1/core/block_pool.py:get_usage, get_new_blocks)); at a gauge of 0.55 a freed prefix survives ≈ 8 s of cold churn against 5 s mean gaps ("Prediction"), so idle prefixes can still be evicted. D1 tests whether the cache comes back when the batch and the gauge are held down. That can still fail: a seed that stays cold and backlogged with the gauge below 0.80 is `stuck_kv_free`, which says the stuck state needs neither a big running batch nor a gauge at 0.80; whether idle prefixes are still evicted is read from `c2.eviction_readout`. A cap above about 34 (if a control's peak is that high) could let the gauge reach 0.80; a seed that stays cold and backlogged with the gauge at or above 0.80 is `stuck_kv_full`, which says the cap did not hold the pool down. The cap values are known before any capped run (the registered computation, below), so the [RESULT] states which regime each seed was in before its label is read.

### Stopping rule (REG-19's and E1's)
- **Order:** seeds 15, 16, 17, 18, 19, one capped run each, fixed before any cap is computed. No interim look at any run's records, verdict or label before the result; no futility stop (none of the outcomes needs one, and an interim look would need its own one-bit rule). Disclosed: the allowed reads still show each seed's outcome bit. The load generator waits for every session until the last planned time plus the 300 s drain (FILE(harness/loadgen.py:209,237-239)); a capped run whose server recovered ends about one healthy session length (≈ 55–58 s) after 4080 s, while one that stays stuck holds sessions at the cap to the deadline, up to ≈ 240 s longer (DERIVED). Run ids carry their launch time, so the gaps between consecutive run ids, and a launch's LAUNCHED and ENDED times, show which seeds recovered (E1 discloses the same for its sweep, FILE(docs/decisions.md:17069)). No step of the stopping rule uses this, and the [RESULT] says so. **No rule, label, threshold or readout of D1 changes after the first capped launch**; a [CORR] after that point is reported in the [RESULT] beside the bits visible when it was written. **Reads allowed while diagnosing a stop** (E1's, FILE(docs/decisions.md:17074)): `tmux has-session`, folder names, `valid` and `failed`, and in a launch log only the lines holding `run_id` or `[run] checks`.
- **Attempts.** Every launch of a seed is one attempt, whatever it left behind; at most three per seed. A seed whose three attempts are spent is not launched again; the other seeds still run, and the queue ends with `QUEUE END`, naming the seeds without a valid run (`not_run`). A pre-launch check that fails (the limit read, the temperature after 30 min, a compute process, a tmux session, the tree, `uv.lock`, the boot id, free disk) launches nothing, spends no attempt, and is not a stop that ends D1; the queue is started again once the cause is removed (after a reboot: 350 W set and a `RENEW=1` session probe recorded in a decisions entry), as E1's (FILE(docs/decisions.md:17072)).
- **Reruns:** an invalid run is rerun unchanged at most twice (three attempts per seed). A `gpu_steady` failure is named "heat, SM-clock steadiness or sample coverage" until its detail is read, and each kind gets the heat rule (FILE(docs/decisions.md:17035)): one rerun after cooling to ≤ 45 °C, and a second `gpu_steady` failure over all D1 runs stops D1. `no_errors`, `power_limit` (a limit other than 350 W) or `manipulation` (the burst did not fill the pool) in a run's `failed` stops D1. Any other check in `failed` of two D1 runs, at any seeds, stops D1 (on the first GPU runs of the cap path a check that fails twice is a question about the harness); the scripts also stop on two at one seed (E1's `MAX_SAME`, FILE(docs/decisions.md:17072)).
- **Lost runs and launches that name no run.** A launch that leaves no `checks.json` (a lost run) counts as an attempt and stops D1 until a new decision (a [DECISION] entry, the owner's or the delegate's), as in E1 (FILE(docs/decisions.md:17072)) and as REG-19's lost runs were handled (FILE(docs/decisions.md:4284), FILE(docs/decisions.md:4383)); an [OPS] entry records the boot id before and after; a lost run is never opened. A launch whose log names no run (no `run_id` line) spends its attempt; a second such launch stops D1 for a new decision (E1's, FILE(docs/decisions.md:17072)).
- **Folder and commit stops.** A folder that no launch log of D1's scripts names, a named run missing from the VM, or a run made at a commit other than the one registered for D1's launches (read from the harness's start line, which holds `run_id` and `git_commit`, FILE(harness/run.py:143)) stops D1 for the owner. Every run with a `checks.json`, valid or invalid, is copied to the Mac and checksum-verified; a run without one is copied by a separate step. No D1 run is removed from the VM before D1's end entry.
- **After any invalid run the queue pauses** (E1's rule, FILE(docs/decisions.md:17034)): each invalid run is written to the ops folder's `state/pause_pending.txt` when its launch log is settled, and no launch, by the queue or by hand, proceeds until a queue start has printed it and set it aside; starting the queue again then applies the rerun rule. **The queue is started again only if no check name stands in `failed` of D1's runs at two or more different seeds**; otherwise D1 stops for a new decision. The check is made from the queue's `RUN … INVALID failed=…` lines alone, and each restart is recorded in an [OPS] entry that quotes those lines.
- **A rerun decision reads only `valid` and `failed`** of `checks.json`; no rerun on any verdict, label or readout.
- **Two valid runs of one seed** (a seed launched again by mistake): nothing is launched for it, both are listed, the earliest counts (`d1.capped_run`, as E1's `first_valid`; FILE(tests/test_d1.py), `test_two_valid_runs_of_one_seed_the_earliest_counts`), and the [RESULT] reports the deviation.
- **Fewer than 3 valid runs** gives `too_few`.
- **The owner halts D1** by an entry headed `## <date> · [DECISION] (owner) D1 halted`; no launch follows its commit.
- **D1 holds the VM** from the first move of the VM's tree to D1's launch commit until its end entry, headed `## <date> · [OPS] D1: the queue ended (QUEUE DONE)`, `## <date> · [OPS] D1: the queue ended (QUEUE END)`, or `## <date> · [OPS] D1 ended by a stop: <the stop line>` (a stop that an entry has decided ends D1). A pause, or a stop that waits for a decision, is not an end. Until the end entry, no other registration's run is launched, and the VM's tree is moved only by D1's scripts or under an owner's entry.
