# Draft 1 (2026-11-13), for review: [DECISION] (delegate) REG-19 resumes for seeds 18 and 19

Proposed heading: `## 2026-11-13 · [DECISION] (delegate) REG-19 resumes for seeds 18 and 19: seed 18's control is rerun as attempt 2; the VM stays at a7bb77a and REG-19's analysis on the Mac runs from a worktree at a7bb77a; the agent sets 350 W itself`

- **Who decides:** the autonomous agent, as delegate (decisions.md 2026-11-13 [DECISION], which names "the REG-19 resume decisions (seed-18 control rerun as attempt 2, the pin rule)").
- **State, from `docs/probe/20261111_reg19/ops/RESUME.md` and each run's `checks.json` only:** REG-19's seeds 15, 16 and 17 each have a control and a burst run on the Mac, all six `valid: True`, `failed: []`. Seed 18's control was lost when the VM went off during it (no `checks.json` expected). Seed 18's burst run and seed 19's pair have not run. `reg19_step` after seed 17 printed `continue: True`. This agent has read no outcome of any REG-19 run.
- **1. Seed 18's control is rerun unchanged, as attempt 2.** REG-19's stopping rule: "Each run once; an invalid run (other than `burst_min_kv_max`) is rerun unchanged, at most twice; no rerun on any verdict or label … A rerun decision reads only `checks.json`." A run cut off by a power-off has no `checks.json` and cannot be valid; the standing practice is that "an interrupted run is kept and rerun" (`docs/status.md`, Open risks). Nothing is read from the lost run for this decision. The lost run is attempt 1; this rerun is attempt 2; if it is invalid by the automatic checks, one more rerun is left (attempt 3), and after that the registration's rule applies ("a seed with no valid pair after its reruns stops the queue").
- **2. Pin rule.** The VM stays at `a7bb77a` with a clean tree, the commit that ran seeds 15–17, until REG-19's [RESULT] is written. The Mac's `main` has since changed `harness/checks.py`, `harness/loadgen.py`, `harness/recorder.py` and `harness/run.py` (commit `5ee6e38`: recorder fix, stricter checks, session cap) and will change further while the queue runs, so `launch6.sh`'s rule (outside docs the Mac may only add) would stop the queue. **New rule (`launch7.sh`): the Mac's HEAD no longer enters REG-19.** Every REG-19 computation on the Mac (`analysis.gate reg19_step` after each pair, and `analysis.gate reg19` once at the end) runs from a git worktree, `/Users/chalshik/Projects/aftershock-reg19-pin`, checked out at `a7bb77a`, with every run folder linked into its `runs/` (ignored there by `runs/*`); the interpreter is the repo's `.venv` (same `uv.lock`). Before each launch `launch7.sh` checks: the worktree is at `a7bb77a` and clean; `a7bb77a` is an ancestor of the Mac's HEAD; `tools/manifest.py`, which is used from HEAD to append the checksum manifest, is unchanged since `a7bb77a`; the config exists at `a7bb77a`; and on the VM, as before, tree at `a7bb77a` and clean, 350.00 W, ≤ 45 °C, no compute process, no tmux session.
  - **Tested without reading a run:** from the worktree, `python -m analysis.gate reg19_inputs` (schedule only) loads `analysis/gate.py` and `harness/workload.py` from the worktree and reproduces the registered schedule table (seed 15: 8253 session / 425 burst requests, λp 1.958 baseline, 2.077 over W).
  - **Difference from seeds 15–17, stated:** their `reg19_step` calls ran from the Mac's HEAD of the time (`a7bb77a` plus commits that `launch4`–`launch6` allowed). Between `a7bb77a` and today's HEAD, `analysis/gate.py`, `load.py`, `derived.py`, `margin.py`, `floor.py`, `tables.py`, `harness/config.py` and `harness/workload.py` are byte-identical (`git diff --quiet`), and `analysis/stats.py` only gained 9 lines (a new function). So the worktree's code equals the code that computed the earlier steps in every function REG-19 calls.
- **3. Power limit.** After a reboot the limit reads 420 W. `launch7.sh` runs `sudo -n nvidia-smi -pl 350` on the VM (the one root command the owner allowed, decisions.md 2026-11-13 [DECISION]) and then reads `power.limit`; a run starts only at `350.00`; each run's own `power_limit` check still fails the run if any sample differs. If `sudo -n` fails, the queue stops and no 350 W run starts.
- **4. The 2026-11-12 check changes (A14) are not deployed for REG-19.** Seeds 18–19 are judged valid by the same checks as seeds 15–17 (the VM's code at `a7bb77a`). REG-19's [RESULT] is computed, as registered, on the runs valid by their stored `checks.json`. After the [RESULT], HEAD is deployed to the VM, and `analysis.recheck` (today's stricter `recorder` and `gpu_steady` checks, read-only) is run on REG-19's ten runs and reported beside the result. If the stricter checks would fail a run the result counts, the [RESULT] entry says so and gives k of n with and without that seed; the registered outcome stands.

Reason: it matches REG-19's control pattern for seed 18, and a half-written `requests.jsonl` or `metrics.jsonl` in it could make `find_runs` raise while it loads every matching folder; nothing in it is needed before. It is then listed under "No checks" in `docs/status.md` and added to the manifest.
